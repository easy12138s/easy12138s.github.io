在上一篇文章中，我们聊到了如何通过结构化提示词来给 Agent 注入“灵魂”。但如果 Agent 只能在对话框里夸夸其谈，那它依然只是一个高级聊天机器人。

真正让 Agent 产生质变的，是它能够调用工具（Tool Use / Function Calling）。

如果说大模型是“大脑”，提示词是“神经”，那么工具就是 Agent 触碰现实世界、操作数字系统的“手脚”。今天我们继续以 Cool Agent 为例，聊聊如何为 Agent 设计一套好用的手脚。

1. 为什么大模型需要“手脚”？

即便是最强大的大模型（如 GPT-4o 或 Claude 3.5），也存在三个致命短板：

  1. 信息滞后：它的知识停留在训练数据截止的那一天。
  2. 逻辑硬伤：复杂的数学运算或精准的时间计算经常翻车。
  3. 无法行动：它不能帮你订票，不能帮你改本地文件名，更不能帮你发邮件。

通过工具调用，Agent 可以实时查询搜索、运行 Python 解释器、或者通过 API 读写你的本地文件。

2. 工具调用的底层逻辑：从 Function Calling 到 MCP

目前主流的工具调用方案主要有两种：

传统的 Function Calling

这是 OpenAI 引领的范式。开发者在请求大模型时，先传一份“工具清单”（通常是 JSON Schema）。

  • 流程：用户提问 -> 大模型判断需要工具 -> 输出“调用指令” -> 你的程序执行代码 -> 将结果回传给模型 -> 模型总结回答。

趋势：MCP (Model Context Protocol)

最近 Anthropic 提出的 MCP 协议 正在重塑这个领域。它不再是每个应用都写一遍 API，而是通过标准化的协议，让 Agent 像插拔 U 盘一样接入各种数据源和工具。这意味着你写好的一个“文件搜索工具”，可以同时无缝运行在不同的 Agent 框架中。

3. 设计工具的三个“黄金法则”

在开发 Cool Agent 的过程中，我总结了三条设计工具的心法：

A. 描述比代码更重要

在大模型眼里，工具的 description 就是它的使用说明书。

  • 坏描述：search_file(name: str)
  • 好描述：search_file(query: str) - 根据关键词模糊搜索本地文档，支持 .pdf 和 .docx 格式，返回文件路径列表。
    描述越精准，大模型“误操作”的概率就越低。

B. 原子化原则

不要试图写一个“万能工具”。把复杂的逻辑拆解成原子化的操作。

  • 错误示范：一个工具完成“下载、解压、分析、总结”。
  • 正确示范：拆分为 download_url、unzip_file、read_content 三个工具。这样 Agent 才能灵活组合，处理意料之外的情况。

C. 容错与反馈循环

工具必须能够“优雅地报错”。当 Agent 调用工具失败时，返回的错误信息（Error Message）应该包含：为什么失败以及建议怎么修。

  • 例如：{"error": "文件路径不存在，请先调用 list_dir 确认当前目录下文件列表"}。看到这个，Agent 就会自动尝试先列出目录，而不是卡在那。

4. Cool Agent 的实战：文件操作的闭环

在 Cool Agent 中，我们为 Agent 接入了文件系统。当你说“帮我把下载文件夹里所有的图片按日期整理”时，它的执行链条是这样的：

  1. Scan: 调用 list_files(path="Downloads")。
  2. Identify: 对每个文件调用 get_file_metadata 获取创建日期。
  3. Plan: 发现缺少对应的目标文件夹，调用 mkdir(path="2024-01")。
  4. Move: 调用 move_file(src, dst)。

每一环节都是通过精准的 API 设计和描述，引导大模型自主决策。

5. 总结与下篇预告

工具调用是 AI 从“感知”迈向“干预”的关键一步。作为开发者，我们不需要造出一个全能的神，而是要为 AI 提供一套足够标准、反馈及时的“工具箱”。
