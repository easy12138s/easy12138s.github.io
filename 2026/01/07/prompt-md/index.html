在系列上一篇文章中，我们聊到了 AI Agent 的核心定义与应用价值。如果说 Agent 是为大模型装上了“手脚”，那么**提示词（Prompt）**就是驱动这双手脚执行任务的“神经中枢”。

很多人把提示词称作“咒语”，仿佛靠几句玄学话术拼接就能让 AI 心领神会。但在 Agent 的工程化构建中，玄学是行不通的。所有“Agent 不听话”、“执行跑偏”的问题，本质上往往是提示词缺乏结构化设计的结果。

今天我们以我的开源项目 Cool Agent 为例，拆解一套适配 Agent 场景的提示词工程化思维。

1. 结构化提示词：Agent 的“任务说明书”

早期的提示词更像零散的自然语言随笔，而在 Agent 开发视角下，优秀的提示词应该是一段可复用、可调试的任务说明书。

目前最主流的结构化范式是 Role-Context-Task-Constraint-Output。我们可以把它想象成给 Agent 设定的“行动框架”。以 Cool Agent 的“智能文件重命名”功能为例：

  • Role (角色)：定义身份边界。
    • 示例：“你是一个专业的文件管理助手，擅长通过阅读文档内容提炼核心主题，并根据规则生成标准化的文件名。”
  • Context (上下文)：补充背景信息。
    • 示例：“用户上传了一份扫描件的 OCR 文本，内容可能包含合同、会议记录或技术方案。你需要帮用户解决文件命名混乱的问题。”
  • Task (任务)：明确核心目标。
    • 示例：“阅读文本，提取出文件类型、关键主体和日期，生成一个简洁的文件名。”
  • Constraint (约束)：划定禁区，这是避免 Agent “乱操作”的关键。
    • 示例：“文件名不得包含特殊字符；必须以 YYYY-MM-DD 开头；严禁在输出中包含任何解释性文字，只输出最终的文件名。”
  • Output (输出格式)：指定结果形式。
    • 示例：“输出格式为纯文本字符串，例如：2026-01-07_字节跳动_合作协议.pdf”。

实战 Tip：在编写时，建议使用 Markdown 的标题（#）或列表来分隔这些模块。AI 对结构化文本的解析效率远高于大段文字。

2. 进阶：让 Agent 精准推理的思维链 (CoT)

在处理复杂逻辑时（比如判断文件的重要性或分类），即使指令清晰，Agent 也可能出现逻辑跳跃。这时就需要引入 Chain of Thought (CoT)。

核心逻辑很简单：在指令中明确要求 Agent “输出你的思考过程”。

在 Cool Agent 中，我们不会让它直接分类，而是引导它：

“在给出分类结果前，请先 analysis 该文档的核心关键词，并对比现有的分类标准。将你的思考过程记录在 <thought> 标签内。”

这种做法强迫模型在生成最终答案前进行推理，能显著降低“幻觉”和逻辑错误的概率。

3. 运行范式：ReAct（推理 + 行动）

我们在上一篇提到，Agent 的核心优势是“自主调用工具”。支撑这一优势的底层范式正是 ReAct (Reason + Act)。

当 Cool Agent 发现自己无法直接处理某个文件时（比如是一个加密压缩包），它的 ReAct 循环会这样运行：

  1. Thought (思考)：我发现这是一个 .zip 文件，且无法直接读取内容。
  2. Action (行动)：调用 list_files_in_zip 工具查看内部结构。
  3. Observation (观察)：工具返回文件列表，其中包含一个 readme.txt。
  4. Thought (思考)：我应该读取 readme.txt 来获取该压缩包的主题信息。
  5. Action (行动)：调用 read_file_content 工具。

这种“思考-行动-观察”的闭环，让 Agent 的决策过程 from “黑盒”变成了“白盒”，极大地提升了任务执行的成功率。

4. 总结：别把 AI 当神，把它当实习生

最后分享一个心态：把 AI Agent 当成一个能力很强，但需要明确指引的“数字实习生”。

  • 如果它执行出错，大概率是你没交代清楚边界（Constraint）。
  • 如果它输出不符合要求，大概率是你没给模板（Output）。
  • 如果它逻辑断了，大概率是你没引导它梳理过程（CoT）。

提示词工程的核心不是写华丽的句子，而是用结构化思维消除歧义。
