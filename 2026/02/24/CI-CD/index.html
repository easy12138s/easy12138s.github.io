在做个人站/作品集这类项目时，我最在意的不是“能不能部署”，而是“能不能稳定、可复用地部署”：写完代码 push 一下，镜像自动构建并推到私有仓库，服务器自动拉取并滚动替换容器，整个过程不需要手工登录服务器敲命令。

这篇文章记录我在 Cool Box（一个 Vite 构建的前端站点）里，落地 GitHub Actions + 阿里云 ACR（私有镜像库）+ ECS 的 CI/CD 实战方案：从工作流拆解、Secrets 设计、服务器准备，到线上最常见的 SSH 坑排查。

1. 目标：一条链路解决“构建-发布-部署”

我希望最终体验是：

  • push 到 main/master → 自动构建前端产物（dist）
  • 自动构建 Docker 镜像 → 推送到阿里云 ACR
  • 服务器通过 SSH 执行：
    • docker pull
    • docker stop/rm
    • docker run -d ... --restart unless-stopped

整个过程只依赖仓库 Secrets，不把任何敏感信息写进仓库。

2. 项目形态：dist + Nginx 的极简镜像

Cool Box 的 Dockerfile 走的是“构建产物 + Nginx”思路：

  • CI 里先 pnpm build 产出 dist/
  • Docker 镜像只负责用 Nginx 托管静态资源

3. Secrets 设计：可读、可迁移、最少集

工作流里我用了一组明确的 Secrets（你可以直接照抄命名）：

阿里云 ACR

  • ALIYUN_ACR_REGISTRY：例如 crpi-xxxx.cn-shanghai.personal.cr.aliyuncs.com
  • ALIYUN_ACR_REPO：例如 cool-box（或 namespace/cool-box，看你仓库组织方式）
  • ALIYUN_ACR_USERNAME
  • ALIYUN_ACR_PASSWORD

服务器 SSH（ECS）

  • ALIYUN_SERVER_SSH_HOST
  • ALIYUN_SERVER_PORT
  • ALIYUN_SERVER_SSH_USER
  • ALIYUN_SERVER_SSH_KEY：私钥内容做 base64 后再存（避免换行/格式问题）

为什么 SSH KEY 要 base64？
因为 GitHub Secrets 多行内容容易出现换行符、缩进、CRLF 的不可控差异；base64 可以把“多行文本”变成“单行安全字符串”，到 CI 里再解码落盘。

4. GitHub Actions：两段式 Job（Build & Push → Deploy）

核心逻辑分两段：

  • build-and-push
    • pnpm 安装依赖
    • 构建 dist
    • 登录 ACR
    • build & push 镜像（latest + 时间戳 + sha 标签）
  • deploy-to-server
    • SSH 登录 ECS
    • 服务器拉镜像并重启容器

我额外加了两个“工程化兜底”：

  • concurrency：同一分支部署互斥，避免连续 push 导致服务器被并发“拉镜像/重启容器”打爆
  • permissions: contents: read：最小权限，符合 GitHub Actions 的安全建议

5. 服务器准备清单（ECS / CentOS 7）

至少要满足：

  • Docker 已安装并可用
  • 服务器能访问 ACR（公网或私网）
  • 端口放行：3000（示例映射 3000:80，你也可以改成 80/443）
  • SSH 公钥登录可用（强烈建议禁用密码登录）

7. 安全与可维护性：我刻意做的三件事

  • 不输出敏感信息：登录 ACR 用官方 Action，避免在日志里出现任何登录细节
  • SSH 强制非交互：BatchMode=yes + PreferredAuthentications=publickey，一旦 key 不通直接失败，不会跑到 password 造成 /dev/tty 的误导错误
  • 并发控制：concurrency 让部署“有序”，减少线上不确定性

8. 总结：一套可复用的 CI/CD 资产

这条链路的价值不在“部署成功一次”，而在“可复用、可迁移、可排障”：

  • 换服务器/换仓库/换项目：改 Secrets 即可迁移
  • 出问题：Actions 日志 + /var/log/secure 能快速定位
  • 迭代：加上 HTTPS、蓝绿发布、健康检查，也不会推翻现有结构

如果你也在做个人站或中小型前端项目，推荐优先采用这套“dist + Nginx + 私有镜像库 + 远程拉取重启”的最小闭环方案：简单，但足够稳定。
